# Velox 反序列化架构

Go 官方 JSON 库的性能不足，社区因此开发了大量“高性能”JSON 库。在 [0.1](./architecture.md) 版本中，Velox 用C实现序列化虚拟机，用Go实现递归下降解析器，分别获得了快速的对象序列化和反序列化能力。Velox 0.1 的反序列化依靠手动内联等许多零散、甚至有些丑陋的手段堆出了不错的性能。这些优化当然有效，但也说明我们缺少一个整体性的方向判断来实现高性能JSON库。因此在 Velox 0.2中，我对反序列化架构的重新设计，明显提升了JSON解析性能。

## JSON 库的风格

Go 生态中已经存在的大量 JSON 库，我把它们按结果形态分成三类。

### 1. 惰性解析

典型代表是 [jsonparser](https://github.com/buger/jsonparser)。它不预先构造完整结果，而是通过访问 API 按需定位和解析值。调用方只读取少数字段时，这种方式可以少做很多工作，内存占用也容易控制。
代价是解析过程会进入业务逻辑。JSON object 的字段顺序没有语义约束，一旦调用方需要组合多个字段、处理嵌套结构或维护跨字段状态，就往往要自行补上一层对象绑定逻辑。

### 2. DOM 解析

DOM 解析先把 JSON 转成库自有的数据结构，再通过统一 API 访问，而不是直接构造宿主语言的对象。C 没有标准的反射机制，因此这种设计在 C/C++ 中最常见。它既是现实所迫，也是性能上的选择：DOM 可以随着输入顺序写入，即使需要回填 container 的位置或长度，也能利用解析栈快速找到对应位置。simdjson 和 yyjson 是这类实现的典型代表。

Go 有完整的反射能力，DOM 风格的 JSON 库相对少一些，比较典型的是 simdjson-go 和 fastjson。fastjson 使用树形 DOM，只在解析阶段识别结构，把数字解析和字符串 unescape 推迟到访问时。与 jsonparser 相比，它访问多个字段时不必反复扫描同一段 JSON，因此在这种使用模式下更有优势。

DOM 的内部格式和能力也服务于各自的目标场景。simdjson 和 yyjson 使用连续内存，fastjson 使用树形结构；yyjson 和 fastjson 支持原地修改。fastjson 最有意义的使用方式是 re-use 模式：解析结果只保持到下一次 `Parse` 之前。这个约定把 DOM 的生命周期缩得很短，parser 因此可以完整复用内部内存，把解析过程中的内存开销压得很低。fastjson 的实现主要也是围绕这种使用方式进行优化。

### 3. 类型绑定

从业务视角看，前面两类更接近 JSON 解析器，因为它们没有直接构造宿主语言的对象。类型绑定利用类型或 Schema 信息，把 JSON 直接映射为目标对象，调用方可以用普通的语言语法继续处理数据，因此也是业务代码中最常见的使用方式。Go 标准库 `encoding/json`、Sonic 和 go-json 都属于这一类。

Go 的反射机制可以提供构造对象所需的完整类型信息，这意味着反序列化并不必然比 DOM 解析更慢。只要提前处理类型信息，解析时就可以按照已知布局直接写目标对象，避免在热路径中反复使用反射。我倾向于把对象绑定看成 JSON 解析的基础原语：**把线性数据变成离散的对象图**。DOM 解析与惰性解析的区别，主要在于绑定的目标格式和发生时机不同。DOM 是绑定到库定义的通用对象，惰性解析则把绑定动作推迟到访问发生时。沿着这个思路，底层解析器不必被上层的使用形式限制，只需要解决如何根据 JSON 构造目标对象即可。

Velox 因此选择对象绑定作为反序列化架构的基础，并在这套能力之上扩展其他使用方式。

## Codec 与虚拟机

在 0.1 中，Velox 的序列化先通过 Go 反射获得类型信息，再把它编译成紧凑的执行指令，最后交给 VM 执行。这个 VM 甚至有子程序调用机制，用来处理递归类型。反序列化却和大部分 JSON 库一样，仍然使用递归下降解析器。这样的实现直接、容易理解，但从对象绑定的角度看，它和序列化之间缺少一种统一的认识。

序列化是根据对象类型，把离散的对象图转成线性数据。反序列化则反过来，根据线性数据构造对象图。JSON的语法是一种上下文无关文法，可以通过下推自动机解析。沿着这个方向再走一步，就可以把 JSON 数据本身看成 VM 的指令：object begin、object field、array begin、scalar、container end 都是指令，解析过程就是执行这些指令并逐步构造对象图。
这是整个设计最重要的出发点。目标类型并不是另一套控制程序，它只是构造对象图时的约束。某个 Go 类型第一次进入绑定路径时，Go 侧通过反射构造并缓存一棵不可变的类型信息树，其中保存对象布局、字段查找表、slot 分配类别和多态描述。这样，执行流来自 JSON 本身，类型信息只需要回答当前指令应该把结果写到哪里，解析和对象绑定也就统一成了同一个 VM的 执行过程。

## C VM 与 Go runtime

决定用 VM 实现反序列化之后，下一个问题是 VM 在哪里运行。C 允许我们精确控制数据布局、寄存器和控制流，也能充分利用编译器的优化能力，是实现高性能 VM 很自然的选择。但反序列化不是一段与宿主语言无关的计算：它最终要构造 Go 对象图，过程中会分配 slice backing、pointer pointee 和 interface 装箱值，会写 map，也可能调用 `json.Unmarshaler`。这些事情依赖 Go 的类型系统、runtime 或用户代码，只能在 Go 侧完成。

这就产生了一个根本矛盾。让 C 自己分配内存，得到的不是 GC 能按 Go 类型管理的对象；每次需要分配或操作 map 都回到 Go，又会让跨语言切换淹没 VM 的收益。更麻烦的是，C VM 直接写 Go 堆时绕过了编译器插入的 write barrier，可能有GC安全问题，除此之外，VM还要服从 goroutine 的栈约束。因此，我们既不能把 C 当成一个与 Go 隔离的解析器，也不能把 Go runtime 当成可以从 C 热路径中随意调用的普通函数库。

社区中的高性能实现通常会避开这个边界。纯 Go 解析器天然运行在 runtime 的规则之内；Sonic 的 JIT 则根据目标类型生成 native 代码，让它直接融入 Go runtime 的执行路径，但它内部的JIT 主要解决代码生成和运行时融合，并不是依赖运行统计的编译优化。对于如何在C执行过程中持续构造 Go 对象，仍然缺少现成的协作方式。
我在Velox里选择让C VM直接构造 Go 对象，同时把只有 Go runtime 才能完成的动作收敛成少数几种 yield。VM 遇到这些动作时，把 phase、游标、容器栈和待处理参数等状态保存在 machine 中，然后退出到 Go；Go 完成相关动作(如分配内存或调用用户方法)后，再resume 回到C VM从对应的 phase 继续执行。整个过程不依赖 C 栈保存状态。

这个机制把VM拆成 native 执行面和 Go runtime 服务面。两边共同推进一次解析，只在职责边界上交还控制权：native 负责扫描、查找、状态机分派和对象写入，Go 负责类型分析、内存分配以及 runtime 操作。
yield 解决了 C VM 调用 Go runtime 的问题，但频繁退出 VM 仍然会抵消 native 执行的收益。Velox 因此不按单个对象请求资源，而是让Go一次准备一批内存，C VM 在其中连续构造对象，整批用完后才 yield。这样，大部分解析时间仍然留在 C VM 内，Go runtime 只在资源补充和必须执行 Go 逻辑的边界上介入。

## GC 安全

C VM 直接写 Go 对象时，编译器不会为这些指针写入插入 write barrier。在 C 中识别每一次指针写入并主动调用 barrier，几乎等于把 Go 编译器的一部分搬进 VM，也会让对象绑定的热路径承担逐字段成本。因此，我没有在 C 中补上逐次 write barrier，而是把 GC 安全建立在整个对象图的构造过程上。这个设计基于以下几点：

1. Go 和 C 的内存布局与对齐规则兼容，C 可以按照类型信息计算字段地址；
2. 对齐的指针写入是原子操作，并发 GC 不会看到写入一半的指针；
3. C 只向受管理的内存或目标对象写入，解析期间这些内存始终由allocator保持GC扫描可追踪；
4. Go GC 以底层内存块为单位进行标记。一块内存被标记为存活时，GC 会按照它的类型布局继续扫描其中的所有指针；
5. 混合写屏障不仅关注新写入的指针，也会保留被覆盖的旧指针。解析完成时只要在 Go 中统一清除这些临时引用，它们原来指向的内存就会被标记为存活；
6. `runtime.KeepAlive` 可以保证输入和目标对象的生命周期长于整个解析过程。

基于这些条件，我将对象图的构造和发布设计成两个阶段。解析期间，Go 侧通过临时引用保持所有相关内存可达，C 新建立的对象关系即使没有被当前的 GC 观察到，也不会导致内存被提前回收。解析完成后，Go 侧统一清除这些临时引用，借助混合写屏障将相关内存标记为存活。
C中无屏障写入只可能影响当时正在进行的 GC轮次，到了下一轮 GC，对象关系已经稳定，自然会被正常扫描。因此，只要构造阶段保证可达，发布阶段补上当轮标记，整个生命周期就是闭合的。GC 保护的粒度也由此从每一次指针写入提升到承载对象图的整块内存，C VM 的热路径不再需要执行 write barrier。

## SIMD 预扫描

VM 的执行模型和 runtime 协作边界确定后，还需要解决它如何从原始 JSON 中取得指令。原始 JSON 中混杂着空白、字符串内容和真正影响语法的字符。如果 VM 一边执行一边识别这些内容，字符串扫描和语法处理就会纠缠在同一个循环里。因此我们参考simdjson，先扫描一遍预先识别引号、转义和结构字符，把字符串起点、结构字符与 scalar 起点提取成结构索引，这相当于把"取指过程"从 VM 执行中解耦出来。
这种解耦是一定性能代价的，SIMD 预扫描需要完整读取一次输入，还要写结构索引，VM 随后再读取它们。JSON 中空白较多时，索引能让 VM 跳过大量无效字节。但是对于 compact JSON，结构位置本来就很密集，额外的一次扫描和索引读写反而显得浪费。simdjson 在 compact JSON 上的这个代价很明显，这也是 yyjson 在这类输入上往往更快的关键原因(毕竟状态机执行是无法并行化的)。Velox 使用simd预扫描，看重的是它把 JSON 整理成清晰的"指令流"，让整个程序的架构更加清晰，而不是因为把simd引入JSON一定更快。事实上，在扫描前缀结构索引的时候，还可以同步做UTF-8和转义校验，这能极大地简化状态机里面处理字符串的复杂度。
SIMD 预扫描由此成为 VM 的输入前端，在保持执行模型清晰的同时，将字符串识别与语法执行分离。

## 总结

Velox 0.2 的设计思路是把对象绑定看成 JSON 反序列化的基础原语，通过反射提前计算出C VM 的只读类型信息(主要是内存分配信息)，C VM 负责执行解析JSON构造出对象，Go runtime 只在分配内存或者需要执行Go逻辑时才介入。我们通过架构设计实现 C VM 可以直写 Go 对象而不在热路径上执行gc write barrier，实现高性能的JSON反序列能力。Velox的内存管理类似于 arena 分配器，成块管理内存也可能因为少量存活对象延长整块内存的生命周期，因此使用时需要注意不要将反序列的对象长期缓存(对于需要长期缓存的数据，良好的实践是构造领域内的对象，而不是复用反序列出来的对象)。前面所述的架构设计只是从根本上解决了此路可通的基础问题，真正实现中还有字段查找、栈空间管理、浮点数解析等许多细节会影响整个反序列的性能，但这些细节不是这套架构的关键基础，因此不在这里详述。这套架构更重要的价值，是让解析、对象构造和 Go runtime 的协作建立在统一的基础上，也为后续的优化和实现更多功能提供了方向和基础。
